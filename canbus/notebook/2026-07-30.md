## FreeRTOS deep dive

Confirmed FreeRTOS works on both platforms, but the two integrations look
quite different day-to-day: STM32 goes through CubeMX/CubeIDE code
generation + CMSIS-RTOS2, Pico is a manual CMake + FreeRTOSConfig.h setup
with no generator. Pico also gets real dual-core SMP (both M0+ cores under
one FreeRTOS instance); STM32 side is single-core only. Neither platform has
a built-in CAN driver usable by FreeRTOS directly — both need
interrupt-driven RX with the ISR just pushing frames onto a queue for a task
to consume. Full notes: [../docs/freertos-notes.md](../docs/freertos-notes.md).

## CLI-only requirement

Want zero GUI tools in the dev loop. Zephyr and Pico+FreeRTOS were already
fully CLI (west / CMake+Ninja). STM32+FreeRTOS was the exception — default
path is STM32CubeMX/CubeIDE. Two CLI-compatible options existed: scripted
CubeMX + Xvfb (keeps ST HAL, needs a display-emulation hack), or libopencm3
(open-source register-level lib, pure Makefile, no GUI/X11 ever). Decided:
**libopencm3**. Full writeup: [../docs/cli-toolchain.md](../docs/cli-toolchain.md).

## Zephyr: one app dir for both boards

Confirmed Zephyr apps are board-agnostic by design — board differences
(CAN controller wiring, LED/button pins) live in `boards/<board>.overlay` +
`.conf` files inside the app dir, picked up automatically by `west build -b
<board>`. App code stays identical across boards via the `zephyr,canbus`
devicetree chosen node and `led0`/`sw0` aliases. So `firmware/zephyr-canbus/`
will be a single directory targeting both the Pico and the STM32 board.
FreeRTOS still needs two separate trees (different build systems). Full
writeup: [../docs/zephyr-single-app.md](../docs/zephyr-single-app.md).

## First app: firmware/zephyr-canbus/

Scaffolded the actual workspace: Dockerfile (Debian trixie-slim, full

## Build-tested for real, found and fixed 4 bugs

Ran `make build` (rpi_pico) end to end — succeeded after two fixes:

- `gcc-multilib`/`g++-multilib` don't exist on arm64 Debian (x86-only host
  packages, irrelevant to Cortex-M cross-compilation) — dropped from the
  Dockerfile's apt list.
- `west init`'s manifest clone isn't shallow even with `--narrow` (that only
  covers `west update`'s module clones) — its full-history clone of Zephyr
  kept dying to a mid-transfer TLS error. Switched to a manual
  `git clone --depth 1` + `west init -l`, plus `http.postBuffer`/
  `http.version HTTP/1.1` git config for resilience on large clones.

`build-rpi_pico/zephyr/zephyr.uf2` (33KB) came out the other end.

Then added `make run`: Zephyr has no QEMU machine model for RP2040, but
`native_sim` (a plain host binary with `zephyr,gpio-emul`-backed GPIO) works
fine for this app. Two more bugs surfaced getting it working:

- `native_sim`'s default target assumes a 32-bit userspace, which doesn't
  exist on this arm64 (Apple Silicon) host — needed the explicit
  `native_sim/native/64` board qualifier.
- Board-specific overlay/conf files must be named after the *full* qualified
  board target (`native_sim_native_64.overlay`, `/` → `_`), not just the
  base board name (`native_sim.overlay` silently wasn't picked up).
- Also: `gpio_pin_get_dt()` right after `gpio_pin_toggle_dt()` doesn't
  reflect the new output state on `gpio_emul` (it always read back 0/"off")
  — real hardware GPIO controllers loop output back to reads, `gpio_emul`
  apparently doesn't. Fixed by tracking LED state in a local variable
  instead of reading it back.

Verified output end to end in the emulator: blink period visibly flips
500ms → 100ms on `[sim] button pressed` and back on `[sim] button released`,
LED state alternates on/off correctly. Full usage/output example:
[../firmware/zephyr-canbus/README.md](../firmware/zephyr-canbus/README.md#running-without-hardware-make-run).
