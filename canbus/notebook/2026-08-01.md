# 2026-08-01

## Board swap: STM32 → ESP32

Corrected the plan — the second board is an ESP32 DevKit already in hand
([Botland ESP32 WiFi+BT 4.2 DevKit](https://botland.com.pl/esp32/8893-esp32-wifi-bt-42-platforma-z-modulem-esp-wroom-32-zgodny-z-esp32-devkit-5904422337438.html),
ESP32-DevKitC-compatible), replacing the previously-planned (never
acquired) STM32 board. Decided this is a full replacement, not a third
platform — still Pico + one other board, just a different other board.

Researched the platform and it's a genuine improvement on several fronts
that mattered to this lab:

- **CLI tooling was never a problem here.** All the `docs/cli-toolchain.md`
  effort (libopencm3 vs. scripted-CubeMX-under-Xvfb) was solving a
  STM32-specific problem. ESP-IDF's `idf.py` (which Zephyr's `west` wraps
  for Zephyr builds) has no GUI code generator at all — CLI-native from
  day one.
- **CAN is built in** (TWAI peripheral, Espressif's name for CAN 2.0), same
  as STM32 would have been — still needs an external SN65HVD230
  transceiver, same as planned.
- **Flashing needs no debug probe.** Plain USB-serial via the onboard
  CP2102 chip + `esptool`, similar convenience to the Pico's UF2. And
  unlike SWD debug probes, this works natively from macOS with zero
  Docker/USB-passthrough workaround — narrows what actually needs the
  Linux-box/RPi detour down to just Pico SWD debugging and the CAN
  adapter.
- **FreeRTOS is already built into ESP-IDF** (not bolted on via a CubeMX
  middleware step), and it's dual-core SMP like the Pico side, just a
  different fork/codebase (ESP-IDF FreeRTOS, based on v10.5.1) rather than
  the same upstream FreeRTOS-Kernel port.

Kept `docs/cli-toolchain.md` and the STM32 section of
`docs/dev-setup-research.md` as historical record rather than deleting —
real research, just for a board no longer in the lab. New doc:
[../docs/esp32-notes.md](../docs/esp32-notes.md) covers the ESP32-specific
findings; `docs/freertos-notes.md` and `docs/zephyr-single-app.md` updated
in place to reference ESP32 instead of STM32.

## Build-tested ESP32 for real — found more infra flakiness

Added the ESP32 board overlay (`boards/esp32_devkitc_esp32_procpu.overlay`
— LED on GPIO32, button on GPIO33, chosen to dodge strapping pins and the
default TWAI pins) and extended the Dockerfile to also install the Xtensa
SDK toolchain (`xtensa-espressif_esp32_zephyr-elf`) alongside the existing
ARM one.

Hit real network flakiness getting this built — not the same bug pattern
as 2026-07-30, worse:

- First attempt: `west update`'s clone of the `lvgl` module died mid-fetch
  (same class of transient failure as before, just a different repo this
  time — confirms it's connection flakiness in general, not one specific
  repo). Fixed by wrapping `west update` in a 3-try retry in the Dockerfile
  (already-fetched modules are left alone on retry).
- Also caught a Dockerfile cache-invalidation bug: the new `pip install
  esptool` line had been appended to the same `RUN` as the expensive `west
  update` step, so any edit to it busted the cache and forced a full
  re-clone of the whole Zephyr workspace. Split into its own layer.
- Second attempt: `west update` succeeded (retry fix worked), but `west sdk
  install`'s SDK tarball download stalled mid-transfer and took **~2 hours**
  before finally erroring out (`IncompleteRead`) — unusually long, real
  network instability today, not just bad luck on one small clone. Added
  the same 3-try retry wrapper to `west sdk install`.
- Third attempt (after explicit go-ahead given the 2-hour cost of the
  previous failure): succeeded. Both `west update` and `west sdk install`
  needed at least one retry internally, confirming the retries were doing
  real work and not just redundant safety margin.

End result: `make build BOARD=esp32_devkitc/esp32/procpu` produces
`build-esp32_devkitc_esp32_procpu/zephyr/zephyr.bin` (130KB), clean build,
no errors. Added `make flash-esp32 PORT=...` to the Makefile — runs
`esptool.py` natively on the host rather than through Docker, since (per
the research above) it doesn't hit the USB-passthrough problem SWD probes
do. Not yet tested against real hardware — no USB cable/port exercised
yet.

Still outstanding: TWAI (CAN) not yet wired into the app or overlay,
real-hardware flash test for both boards, Pico SWD debug-probe flashing
still unexercised.

## Added and verified the ESP32 emulator (Espressif's QEMU fork)

User asked whether an ESP32 emulator exists. Unlike RP2040 (no QEMU
support at all in Zephyr), ESP32 does: Espressif maintains its own QEMU
fork with real Xtensa CPU + peripheral emulation, a step up from
`native_sim`'s host-binary-with-faked-GPIO approach. Implemented it for
real rather than just describing it, per the usual practice this session
of verifying rather than guessing.

Added to the Docker image as a prebuilt binary release (not built from
source — much faster, skips the X11/SDL/GTK build-dep chain):
`qemu-xtensa-softmmu-esp_develop_9.2.2_20260417-aarch64-linux-gnu.tar.xz`.
Added `make run-esp32-qemu` to the Makefile.

Made one avoidable mistake and hit two real bugs getting it working:

- **Mistake**: added the new `libpixman-1-0`/`libslirp0` apt packages to
  the *existing* shared apt-get layer instead of a new one, which busted
  the Docker cache for every layer after it — including the expensive
  `west update`/`west sdk install` steps — forcing an unnecessary full
  re-clone. Caught it partway through, fixed by moving the new packages to
  their own layer, and restarted the build (which then correctly hit the
  cache from the last known-good image instead of re-cloning again).
- **Bug**: `qemu-system-xtensa --version` failed with a missing
  `libgcrypt.so.20` — not in Espressif's documented dependency list
  (`libpixman-1-0`, `libsdl2`, `libslirp0`). Added `libgcrypt20`.
- **Bug**: first real run got past the ROM bootloader (`ets Jul 29 2019
  12:21:46...` — confirms genuine hardware emulation, not a stub) but then
  Zephyr's `esp32` SoC init rejected the chip as an unsupported revision —
  QEMU emulates chip revision 0, real ESP32-WROOM-32 modules are typically
  newer. Fixed with `CONFIG_ESP32_USE_UNSUPPORTED_REVISION=y` in the new
  `boards/esp32_devkitc_esp32_procpu.conf` (harmless for real hardware,
  only widens acceptance).
- **Bug**: even after the revision fix, boot still failed with
  `invalid header: 0x00000100` — turned out `zephyr.bin` needs to sit at
  flash offset `0x1000` inside the padded 4MB image handed to QEMU, not
  offset `0`. (Same offset `make flash-esp32` already writes to on real
  hardware via `esptool`, so this was really just "match the real flash
  layout," obvious in hindsight.) Fixed the `dd` command in the Makefile
  target.

After all four fixes, `make run-esp32-qemu` boots cleanly end to end:

```
ets Jul 29 2019 12:21:46
...
*** Booting Zephyr OS build v4.4.0 ***
led on (period=500ms)
led off (period=500ms)
...
```

No interactive button-press demo this way (QEMU's touch-pin keyboard
simulation is hardwired to GPIO01/02/12/13, this app's button is on
GPIO33) — but that's fine, its value here is different from `native_sim`'s:
it's booting against a much more realistic hardware/peripheral model (real
ROM bootloader, real chip-revision checks, real flash layout), catching
issues `native_sim` structurally can't.

Docs updated: `docs/esp32-notes.md` gets the full writeup, `CLAUDE.md` and
`firmware/zephyr-canbus/README.md` both mention it.
