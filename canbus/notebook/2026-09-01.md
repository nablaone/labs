# 2026-09-01

## CAN bus round-trip debugging — long chase, real bug found and fixed

Picked up from [2026-08-26.md](2026-08-26.md)'s Stage B work: `can send`/
`can sniff` on the ESP32 and `cantool.py send`/`sniff` on the Mac had
tested clean that day. Today's session started with "check if the board
is on, and if the CAN bus is connected" after a full physical reconnect,
and turned into a long investigation because the Mac→ESP32 direction
(sending from the CANable2 dongle, receiving on the ESP32) was
unreliable, while ESP32→Mac stayed rock solid throughout.

**Wrong turns, in order, each ruled out by a concrete test:**

1. **GPIO/wiring theory** — re-tested `can xcvr` self-test repeatedly;
   always passed. Not the ESP32 side.
2. **CANH/CANL wiring theory** — multimeter check across CANH/CANL: 60Ω
   on both ends (healthy — two 120Ω terminators in parallel, per the
   check in [docs/diagnostics.md](../docs/diagnostics.md)). Also found
   and fixed a genuine CANH/CANL swap during a physical move to a
   different location — worth noting this one **was** real and did need
   fixing, even though it wasn't the whole story.
3. **CANable2 firmware theory** — raw slcan protocol commands (`C`, `S6`,
   `O`, `t...`) got zero response over the Mac's serial connection to the
   dongle, while `V` (version query) returned a git-describe string
   instead of the standard slcan version format. Looked exactly like
   non-standard/broken firmware. **Refuted** once the user plugged the
   same physical dongle into the Linux box and ran `candump`/`cansend`
   there — both worked cleanly. Turned out the firmware's own docs state
   "this firmware currently does not provide any ACK/NACK feedback for
   serial commands" — the missing `\r` responses were expected behavior,
   not a sign anything failed. Confirmed the firmware does track state
   correctly via the `E` (error register) query, which responded
   `CANable Error Register: 0` after a real open+send sequence.
4. **gs_usb/candleLight firmware theory** — briefly suspected the dongle
   might be running gs_usb (binary protocol) rather than slcan (ASCII),
   with the `/dev/cu.usbmodem*` serial port just being an unrelated debug
   console. Tested via python-can's `gs_usb` backend (`pip install
   "python-can[gs_usb]"`, needs `pyusb` + `libusb` — already present via
   Homebrew) — its own device scan found **zero** devices, refuting this
   theory. Combined with the dongle's PID (`16d0:117e`) matching the
   Linux box's already-confirmed-slcan unit, this is genuine slcan
   firmware.

**Real, reproducible finding**: raw pyserial commands to the dongle
(`C`\r → wait → `S6`\r → wait → `O`\r → wait → `t...`\r, with real
inter-command delays) succeeded at least once (`300#CC` arrived on the
ESP32's `can sniff`), while `cantool.py`/python-can's `slcan` backend
never delivered a frame across many attempts — even when manually
re-running the same C/S6/O sequence (with delays) against the *same*
`bus.serialPortOrig` right after python-can's own (delay-free,
back-to-back) auto-init. That pointed at python-can's slcan.py firing
`close`/`set-bitrate`/`open` with no gaps between them as the likely
culprit, since the firmware apparently needs those spaced out.

**But then the raw approach also failed on a later retry** (`700#FF`)
with the identical method and delays — proving the issue was genuinely
**intermittent**, not a clean, deterministic python-can-vs-raw
difference. Combined with a spontaneous ESP32 serial glitch (garbled
reads, a repeated-line print artifact) that turned out to be transient
read-timing noise on the test-script side (confirmed via a full boot
capture with an explicit panic/watchdog-signature grep — clean, no
`Guru Meditation`/`abort()`/`TG0WDT`/etc.), the most likely remaining
explanation is a marginal USB/cable/port-level connection on the Mac
side — not fixable by more protocol-level guessing.

**Real bug found and fixed along the way**: while testing with the
*actual* `cantool.py sniff` command (backgrounded, to script a timed
test) instead of ad hoc inline python-can scripts, its output appeared
to be empty — looked like another reception failure. Turned out to be a
genuine bug: Python fully buffers `stdout` when it isn't a real
terminal (piped/redirected/backgrounded), so `print()` calls sat
unflushed until the process exited. Sending the running process a real
`SIGINT` (not `TaskStop`, which might not map to it) and reading the
output *after* exit showed the frame had actually been received the
whole time. Fixed with `flush=True` on `cmd_sniff()`'s prints — doesn't
affect a human running `make can-sniff` at a real terminal (auto
line-buffered there already), but matters for any redirected/piped use.

**Also simplified**: `can sniff` on the ESP32 used to wait for Enter to
stop (via non-blocking UART polling,
`uart_get_buffered_data_len()`/`uart_read_bytes(timeout=0)` each loop
iteration). Replaced with a fixed 30s timeout — simpler, and removes a
whole mechanism (plus the CRLF-leftover-byte quirk it needed a
`uart_flush_input()` workaround for) that wasn't earning its complexity.

**End state**: after all of the above, the user reported it working —
bidirectional CAN traffic confirmed between the ESP32 and the CANable2.
Given the intermittency observed along the way, worth keeping an eye on
whether Mac-side sends stay reliable in future sessions; if not, consider
trying a different USB cable/port, or preferring the raw-pyserial
approach with real inter-command delays over python-can's `slcan`
backend for `cantool.py send` specifically.

## Split main.c into per-module files (same day, after the above)

After disabling the `led on/off` log spam, restructured
`firmware/esp32-idf/main/main.c` from one file into a per-module layout,
ahead of building more real nodes (motor/controller/panel — see
[../docs/project-charter.md](../docs/project-charter.md)). Explicit goal
stated by the user: keep the same codebase/pattern across every future
node, each task as an init-part + a loop, hardware modules configured
in/out at compile time (NVRAM-backed runtime config planned but not
implemented).

**New layout** (`firmware/esp32-idf/main/`):

- `node_config.h` — the file a new node copies/edits: `NODE_ENABLE_*`
  compile-time flags, pin assignments, `FIRMWARE_VERSION`. Nothing else
  should need to change per node.
- `state.c`/`.h` — the shared "excitement counter" + heartbeat period,
  mutex-protected. Owns the `counter` CLI command.
- `led_task.c`/`.h`, `button_task.c`/`.h` — `xxx_task_init()` (GPIO setup)
  + `xxx_task()` (the loop), unchanged behavior from before the split.
- `heartbeat_task.c`/`.h` — same init+loop shape; also owns `rate` (it's
  the natural owner of its own tunable, rather than state.c knowing about
  CLI at all).
- `display_task.c`/`.h` — **new task**, extracted from `app_main()`'s
  inline `while(1)` loop (the "log the counter every 10s" logic). This
  was the one piece of real behavior change the user asked for
  explicitly: "the code that displays a message every 10s should be
  another task."
- `can.c`/`.h` — TWAI driver + self-test + send/sniff. Doesn't fit the
  task init+loop shape (no background loop of its own, it's entirely
  CLI-command-driven) but still gets its own file per the same
  one-module-per-file convention, since it's exactly the kind of
  "hardware code" the user wants each future node's stack to layer on.
- `console.c`/`.h` — `esp_console`/linenoise setup, the `console_task`
  loop, and the core `help`/`version`/`exit` commands. This is "the same
  debug strategy" line item — every node gets this file verbatim.
- `main.c` — now just orchestration: `state_init()`, `console_init()`,
  each enabled module's `_init()`, CLI command registration, then
  `xTaskCreate()` for each enabled task. Wrapped in `#if NODE_ENABLE_*`
  guards from `node_config.h` so a node that doesn't need, say, the
  button task just flips one flag rather than editing this file.

Each module also got its own `ESP_LOG` tag (`can`, `display`, `main`)
instead of the old single shared `"canbus"` tag — reads better once
there's more than one hardware module logging, and costs nothing.

**Verified identical behavior on real hardware** after the split: boot
log shows `CAN self-test: PASS` under the new `main:` tag, `app_main()`
now returns cleanly (logged by ESP-IDF's own `main_task: Returned from
app_main()`, expected now that the display loop is a real task rather
than app_main's own infinite loop), `display: excitement counter = N`
confirms the extracted task runs on its own schedule, and a full CLI
pass (`version`, `counter`, `rate 5`, `can xcvr`, `exit`) all worked
exactly as before the split.

One process note: hit `make: *** No rule to make target 'flash'` once
mid-session — turned out to be forgetting that `cd` in one Bash tool
call doesn't persist to the next call in this harness; re-running with
an explicit `cd firmware/esp32-idf &&` prefix fixed it. Not a real
build/Makefile problem.

## display_task now broadcasts the counter over CAN (same day)

Extracted a plain `can_send(id, data, len)` from `can.c`'s CLI-only
`cmd_can_send()` (which now just formats/parses and calls it) so other
modules can put a frame on the bus without going through the CLI. Wired
`display_task` to call it every 10s alongside its existing log line:
4-byte little-endian counter value on ID `0x7F0`.

ID choice: deliberately high in the 11-bit standard space. CAN
arbitration is lowest-ID-wins, so a high numeric ID is the *lowest*
priority on the bus — right for a non-critical periodic debug broadcast
that should never delay real control traffic later. Landed in
[../docs/can-message-spec.md](../docs/can-message-spec.md)'s diagnostics
band (`0x700`–`0x7FF`) since this genuinely is diagnostic/debug data, but
picked `0x7F0` specifically to stay clear of that doc's `0x7NN`
`NODE_HEARTBEAT` pattern — this broadcast is experimental, not that
registered message.

Verified end to end on real hardware: CANable2 listener caught three
consecutive frames on `0x7F0` (`13 00 00 00`, `1D 00 00 00`,
`27 00 00 00` → 19, 29, 39 decimal), each exactly +10 from the last and
~10s apart, matching `heartbeat_task`'s 1/sec increment over the 10s
display interval. Cross-checked against the ESP32's own `display:
excitement counter = 59` log line a few cycles later — consistent with
the same counter, same source.

## button_task now broadcasts on press too (same day)

Extracted the little-endian-u32-payload part of `display_task`'s
broadcast into a `can_send_u32(id, value)` wrapper around `can_send()`
(in `can.c`/`.h`), then wired `button_task` to call it: every 100ms poll
where the BOOT button reads pressed, alongside the existing counter
increment, it now also broadcasts the new counter value on `0x110`.

ID choice: `0x110`, a scratch ID in
[../docs/can-message-spec.md](../docs/can-message-spec.md)'s unallocated
gap (`0x100`–`0x6FF`) — numerically lower (so higher-priority under
CAN's lowest-ID-wins arbitration) than `display_task`'s `0x7F0`, since a
button press is a more time-sensitive event than periodic telemetry.

First verification attempt was inconclusive — an 8-10s CANable2 listen
window caught only `0x7F0` frames (the ongoing periodic broadcast), zero
on `0x110`, most likely just a timing miss on when BOOT was actually
held versus when the listener started. Re-tried with a clearer
ready/go cue and the user confirmed it works.

## New module: lcd_task (HD44780 over I2C), plus a boot-time I2C scan

Added `lcd_task.c`/`.h` for a 16x2 HD44780 character LCD driven through
a PCF8574 I2C backpack — the next hardware module, following the same
init+loop task shape as the rest of `main/` (see
[../firmware/esp32-idf/README.md](../firmware/esp32-idf/README.md)'s
"Module layout" section for the full design). New I2C pins in
`node_config.h`: GPIO32 (SDA) / GPIO33 (SCL), free/non-strapping and
distinct from CAN's GPIO21/22.

Public API is `lcd_display(line1, line2)` — mutex-protected, and
deliberately non-blocking/async: it only updates an in-memory
line1/line2/dirty struct and returns immediately (skipping the update
entirely if the text is unchanged from what's already shown), while
`lcd_task`'s own loop wakes every `LCD_UPDATE_MS`, and only if dirty
does it snapshot the text, release the mutex, and *then* do the
(comparatively slow) I2C write — so a caller on another task never
blocks on that transaction. Uses IDF 5.3's new `driver/i2c_master.h`
API rather than the legacy `driver/i2c.h`. Also added an `lcd <line1>
<line2>` CLI command for manual bring-up testing.

Verified end to end on real hardware (build, flash, boot capture) with
the LCD not yet physically wired: `main`/`can` come up exactly as
before (CAN self-test PASS, clean `app_main()` return) and `lcd`
non-fatally logs that nothing responded at the configured address,
confirming the "board still runs fine without this hardware present"
design goal.

**Follow-up request**: "add i2c probe on boot" — added a full I2C
address-space scan (`0x08`-`0x77`) in `lcd_task_init()`, logging every
address that responds. Useful generally for bring-up (PCF8574 backpacks
commonly ship at either `0x27` or `0x3F`, no reliable way to know which
without probing) and specifically because it caught a real, if minor,
bug: the first version had a *separate* single-address probe of
`LCD_I2C_ADDR` right after the scan, gating whether the HD44780 init
sequence ran. On the very first boot capture, the scan correctly found
nothing (as expected — the LCD isn't wired), but that separate re-probe
of the same address (`0x27`) reported success anyway, so the code
proceeded to run the init sequence and logged "display ready at 0x27"
despite nothing being connected. An unloaded/floating I2C bus (internal
weak pull-ups only, no device on the other end) can ACK a lone probe
inconsistently from one attempt to the next — so two separate probes of
the same address disagreeing isn't itself surprising, but relying on
the second one was wrong. Fixed by making the scan the single decision
point: it now returns whether `LCD_I2C_ADDR` was among the addresses
that responded, and that's what gates the init sequence — no second
probe. Re-verified on real hardware: scan and verdict now agree
("no devices found on the bus" / "no response from 0x27 during scan").

## LCD bring-up: physical wiring, then i2c_master_probe() itself was the bug

With `lcd_task` in place and consistently reporting "no response from
0x27", the LCD backpack got physically wired up (GPIO32 SDA / GPIO33
SCL / shared GND / VCC from 3V3 rather than 5V, since ESP32 GPIOs
aren't 5V-tolerant). Scan kept finding nothing even with the backlight
visibly lit, which kicked off a long elimination chase:

1. **GND/pin continuity** — confirmed shared GND, confirmed 3.3V idle
   on both SDA/SCL (pull-ups present and working), confirmed SDA/SCL on
   the right physical pins. Tried swapping SDA/SCL as a common-mistake
   check. Still nothing.
2. **Independent verification via Raspberry Pi** — moved the same
   backpack to a Pi and ran `i2cdetect -y 1` (after first trying bus 2,
   which turned out to be a *different*, also-present bus on this
   particular Pi — `i2cdetect -l` was needed to find the right one).
   Bus 1 found the backpack cleanly at `0x27`. This proved the module
   itself was fine, moving suspicion fully onto the ESP32 side.
3. **Pin-specific theory** — moved `I2C_SDA_GPIO`/`I2C_SCL_GPIO` from
   GPIO32/33 to GPIO26/27 (also free/non-strapping) to test whether
   those two specific pins were somehow bad. Identical "no response"
   result on the new pins too — ruled out a per-pin hardware defect.
4. **The actual bug**: added one-off diagnostic logging of the *real*
   `i2c_master_transmit()` result (bypassing `i2c_master_probe()`
   entirely) — it returned `ESP_OK` on the very first try. Confirmed:
   `i2c_master_probe()` is unreliable on this IDF 5.3.2 / hardware
   combination, reporting failure even against a device proven present
   by two independent tests (the Pi, and now the ESP32's own real write
   path). All the wiring/pin-swapping in steps 1-3 was chasing a ghost
   created by a bad presence-detection API, not a real fault.

**Fix**: `pcf8574_write()` (the one place that actually talks to the
PCF8574) is now the source of truth for presence, not
`i2c_master_probe()`/the scan — `lcd_task_init()` gates the HD44780
init sequence on a real write's result instead. The scan stays, but
purely as an informational bring-up aid now (see its doc comment).
GPIO26/27 stayed as the final pin choice, purely because that's what
was already wired/verified by this point — no functional reason to
move back to 32/33.

**Second bug, found once presence detection was fixed**: the physical
screen showed garbage on boot instead of blanking cleanly. Turned out
real `i2c_master_transmit()` writes — not just `probe()` — are also
genuinely unreliable on this bus (`I2C software timeout` errors seen
mid-sequence), most likely weak pull-ups (only the ESP32's internal
~45kΩ ones are engaged) plus breadboard/jumper-wire capacitance. A
single dropped nibble transaction mid-byte desyncs the HD44780's 4-bit
nibble pairing for everything written after it, which is exactly what
"garbage" looks like. Mitigated in software (a real fix would be
external 4.7kΩ pull-up resistors, not attempted here):
- `pcf8574_write()` retries up to 5 times with a 2ms gap between
  attempts (immediate back-to-back retries tended to hit the same bad
  bus condition again).
- I2C clock dropped from 100kHz to 20kHz, and `glitch_ignore_cnt`
  raised from the typical default of 7 to 20, both for more timing/
  noise margin.
- `hd44780_init_sequence()` explicitly writes 16 spaces to both rows
  (via the same `hd44780_write_line()` path `lcd_display()` uses) on
  top of the standard HD44780 clear command, rather than trusting a
  single clear command to reliably land on a bus this marginal.

Also briefly suspected the boot-time scan's 112 failed probes might be
leaving the peripheral in a degraded state that the real writes right
after it then had to recover from — disabling the scan for one test
build showed the same failure-then-recovery pattern starting
immediately, ruling that out too. The failures are a real, pin-
independent, scan-independent property of this particular bus, and
happen to settle into a clean run after roughly the first second of
real traffic every time.

Verified end to end on real hardware: boot log shows `display ready at
0x27` with a clean screen (backlight on, no garbage), and `lcd hello
world` from the CLI renders correctly on both rows.

Confirmed both the ESP32 (USB-serial) and the CANable2 dongle healthy
after reconnecting everything: boot log clean (CAN self-test PASS, LCD
ready), and the CANable2 caught real `0x7F0` frames on the bus (not
just the ESP32's internal self-test loopback) — full round-trip intact.

Verified on real hardware: serial log shows the three parameters

...), and a CANable2 listen confirmed frames on `0x7F0` arrive once per
full 6s cycle (3 params × 2s) with the counter value incrementing by 6

## LCD I2C reliability: real pull-ups added, and a correction

Asked "is it normal?" after noticing the display cycling worked but the
serial log was full of `I2C software timeout` errors on nearly every
write, being silently absorbed by `pcf8574_write()`'s retry loop. Answer
was no -- a healthy bus shouldn't need that much retrying -- so real
external pull-up resistors got added to SDA/SCL.

First check after adding them was a false alarm in the *other*
direction: the failure pattern (26 failures at boot, at millisecond-
identical timestamps) was **byte-for-byte identical** to a capture taken
before the pull-ups went in. Read literally, that looked like the
pull-ups made zero difference -- but perfectly reproducible, identical-
to-the-millisecond timing across two independent real-hardware resets
isn't what analog noise looks like; noise varies. That pointed instead
at the earlier "fix" (I2C clock slowed to 20kHz, `glitch_ignore_cnt`
raised from 7 to 20) as itself being the deterministic cause, unrelated
to the pull-ups.

Reverted to standard settings (100kHz, `glitch_ignore_cnt=7`) with the
new pull-ups in place, and the failure count dropped sharply -- from a
consistent ~26 per burst down to single digits (5, 2, 4, 2, 1...),
*varying* cycle to cycle rather than repeating exactly. That variability
is what confirmed this really was analog noise being reduced, not
another deterministic artifact. So both things were true, just not in
the order first assumed: the pull-ups were the real fix, and the
earlier slow-clock/high-glitch settings were an unhelpful overcorrection
that happened to mask the improvement in the first same-settings
comparison. Kept the retry loop in `pcf8574_write()` regardless -- the
failure rate didn't reach zero, so it's still a useful safety net, just
no longer doing nearly as much work.

## Build/flash speed: what's actually in the binary, and cutting build time

Asked "how big is the binary, why is build/flash so slow, why so many
modules." Answers, in order:

- **Binary size**: 286,272 bytes (~280 KiB) in a 1 MiB app partition --
  73% free, not bloated.
- **Flash speed**: the Makefile's `flash` target deliberately passes
  `--no-stub` to `esptool` (talks straight to the slow ROM bootloader
  instead of uploading esptool's fast RAM stub first) for portability --
  Debian's `esptool` apt package ships without the prebuilt stub blobs,
  so this is what makes the same Makefile work on both a Mac's
  pip-installed `esptool` and a Debian box. Costs a lot of raw transfer
  speed (~80 kbit/s instead of several hundred+) as the tradeoff.
- **Build speed / "why so many modules"**: `idf.py build` compiles
  ESP-IDF's *entire* bundled component set by default -- wifi_provisioning,
  mqtt, spiffs, fatfs, json, protocomm, espcoredump, etc. -- regardless of
  whether the app needs them, and only trims the final *link*, not the
  build. Confirmed via `idf.py size-components` (the authoritative
  per-archive linked-size breakdown): none of those show up in the actual
  binary at all. First guess at a fix was disabling WiFi via
  `sdkconfig.defaults` (`CONFIG_ESP_WIFI_ENABLED=n`) -- checked the
  Kconfig source in the toolchain image and found `ESP_WIFI_ENABLED` has
  no user-facing prompt at all (`bool` / `default y if SOC_WIFI_SUPPORTED`
  -- a hardware-capability flag, not a real switch), so that change was
  silently inert. Confirmed by a full clean rebuild showing the exact
  same step count (983) before and after -- removed the ineffective
  `sdkconfig.defaults`.

Real fix: `set(COMPONENTS main)` in the top-level `CMakeLists.txt`
before `project()` -- the documented way to restrict which components
`idf.py` even considers, rather than trying to disable individual
features. `main`'s own `(PRIV_)REQUIRES` chain plus ESP-IDF's baseline
components (freertos, esp_system, bootloader, partition_table, etc.)
still get pulled in automatically. Full clean build dropped from 983 to
577 steps (~41% fewer) and ~43s to ~24s wall time; binary even shrank
slightly (280,272 bytes, down ~6KB) since less generic init/config code
got linked in. Verified on real hardware after the change: boots
identically (CAN self-test PASS, LCD ready, display cycling correct),
and a CANable2 listen confirmed real `0x7F0` CAN traffic still arrives.
