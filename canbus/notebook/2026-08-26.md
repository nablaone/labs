# 2026-08-26

## CAN Stage A bring-up — long detour through wrong hardware theories, real bug was firmware

Implemented [docs/can-bus-bringup-plan.md](../docs/can-bus-bringup-plan.md)'s
Stage A: SN65HVD230 transceiver (turned out to be a Waveshare 3945) wired
to the ESP32 on GPIO21/22 (D21/D22), `TWAI_MODE_NO_ACK` self-test loopback.
Confirmed board's `D21`/`D22` silkscreen really is GPIO21/GPIO22 (via
search, since no multimeter on hand) — this is the "ESP32 DEVKIT V1"
30-pin board type.

**First self-test run: FAIL.** `twai_receive()` timed out, but
`twai_get_status_info()` showed *zero* errors of any kind (tx_err, rx_err,
tx_failed, arb_lost, bus_err all 0) and `msgs_to_tx` drained to 0 — i.e.
the driver believed transmission succeeded cleanly, but nothing ever came
back. That "clean success, silent RX" signature drove a long chain of
hardware theories, all wrong:

1. **Wrong-pin theory.** Swapped CAN_TX/RX to TX2/RX2 (GPIO17/16), then to
   D0/D2 wasn't reachable (turned out GPIO0 has no separate header pin on
   this board, only the BOOT button) — identical failure every time.
   Ruled out D21/D22-specific wiring.
2. **Power theory.** Rewired VCC/GND. Symptom actually *changed* after
   this — `msgs_to_tx` started sticking at 1 (frame stuck waiting to
   transmit, controller reading bus as permanently busy) instead of
   draining to 0. Suspected CTX shorted to GND or CANH/CANL shorted
   together during the rework.
3. **Firmware/wiring mismatch (real, but not the root cause).** Diagnosing
   the power-rewire symptom change, noticed the GPIO status log said
   `GPIO[16]`/`GPIO[17]` — the board was still running the earlier
   TX2/RX2 diagnostic build, because the source had been reverted to
   GPIO21/22 and rebuilt but never **re-flashed**. All the "rewire power,
   recheck CTX" work in between was against stale firmware driving
   different physical pins than what was being wired. Re-flashed the
   correct build — back to the original `msgs_to_tx=0` signature.
4. **Termination theory.** Found the Waveshare 3945's product page didn't
   mention a termination jumper — hypothesized missing 120Ω. User pointed
   at the actual schematic
   ([PDF](https://files.waveshare.com/upload/c/c5/SN65HVD230-CAN-Board-Schematic.pdf)):
   the board has a **fixed, always-on 120Ω** across CANH/CANL (R2, not a
   jumper) and `Rs` biased through a 10KΩ to GND (valid slope-control
   mode). Termination was never the problem — ruled out definitively by
   reading the actual schematic instead of guessing from a product
   listing.
5. **Decisive test:** ran a bare jumper wire directly from D21 to D22,
   transceiver disconnected entirely. **Still failed, identically.** That
   ruled out the transceiver, the wiring to it, and termination all at
   once — the bug had to be in firmware.

**Actual root cause**, found by reading ESP-IDF's own
`examples/peripherals/twai/twai_self_test`: the example sets
`.self = 1` on the transmitted `twai_message_t` (self-reception request).
`TWAI_MODE_NO_ACK` alone does *not* cause self-reception — `twai_transmit()`
reports success regardless of whether the frame is queued for local
receipt; that flag is what actually requests the loopback. Without it,
`twai_receive()` will time out **no matter how good the wiring is**, which
is exactly why the direct-jumper test in step 5 still failed. Added the
flag to `can_selftest()` in
[firmware/esp32-idf/main/main.c](../firmware/esp32-idf/main/main.c) — self-test
passed immediately, both with the direct jumper and with the real
transceiver reconnected.

**Lesson for next time**: when a self-test shows "clean success, silent
receive, zero errors" *consistently across every wiring permutation
including bypassing the suspect hardware entirely*, stop trusting the
hardware theory and go re-read the reference example line by line — the
decisive test (bare jumper wire, no transceiver) should have been step 1,
not step 5.

Also used this session to bring up a secondary, independent verification
path: a CANable2 (separate unit, not the one on the Linux box) plugged
directly into the Mac, talked to via `python-can`'s `slcan` backend in a
scratch venv (no SocketCAN needed on macOS). Confirmed it enumerates as
slcan/CDC-ACM firmware, same as the Linux box's unit. Useful as an
independent listener during debugging (step 5's conclusion didn't depend
on it, but it corroborated "nothing reaching the physical bus" earlier in
the process). Not yet decided whether Stage B uses this Mac-side path or
the Linux box's `can0` as originally planned — see
[docs/can-bus-bringup-plan.md](../docs/can-bus-bringup-plan.md#open-questions).

Stage A is now confirmed passing end to end on real hardware. Stage B
(`TWAI_MODE_NORMAL` against a real peer) not started yet.

## CAN CLI restructure + Stage B round-trip, same session

Split the single `can` self-test command into subcommands and added real
send/sniff, all in `firmware/esp32-idf/main/main.c`:

- `can loop` / `can xcvr` — same underlying self-test
  (`can_run_selftest()`), different expected physical setup (bare D21-D22
  jumper vs. real transceiver) reflected in the printed instructions, not
  in the code.
- `can sniff [seconds]` — prints received frames as `<id_hex>#<data_hex>`
  for a fixed duration (no interruptible read in this CLI, so bounded
  rather than open-ended).
- `can send <id_hex>#<data_hex>` — parses and transmits one frame, same
  syntax as `can-utils`' `cansend`.

Driver now defaults to `TWAI_MODE_NORMAL` at boot (real bus, real ACKs);
`can_reinit()` does a stop/uninstall/reinstall to drop into
`TWAI_MODE_NO_ACK` temporarily for `can loop`/`can xcvr`, then switches
back. The boot-time auto self-test uses the same
reinit-test-reinit-back path (`can_run_selftest()`).

Added `firmware/esp32-idf/cantool.py` as the Mac-side counterpart —
`python-can`'s `slcan` backend talking directly to a CANable-style
dongle's serial port (no SocketCAN needed on macOS), same
`<id_hex>#<data_hex>` syntax so a frame copy-pastes between ESP32 CLI and
Mac shell. Own venv (`.cantool-venv/`, gitignored) since Homebrew Python
refuses unmanaged `pip install` — `make can-sniff`/`make can-send` in
`firmware/esp32-idf/Makefile` create it on first use. Needed both
`python-can` and `pyserial` explicitly (slcan backend depends on the
latter but doesn't pull it in automatically).

**Confirmed real bidirectional bus traffic** against the CANable2 still
attached to the Mac from the Stage A debugging above:
- `can send 123#DEADBEEF` on the ESP32 → received via `cantool.py sniff`
  on the Mac.
- `cantool.py send 321#CAFEBABE` on the Mac → received via `can sniff` on
  the ESP32.

Both directions, matching syntax on both ends, no code changes needed
between the two tests. Stage B is now effectively done too, just not yet
against the Linux box's `can0` as originally planned (see the open
question in the bring-up plan).

## Sniff: switched from fixed-duration to interruptible, each side its own way

Changed `sniff` on both sides from "run for N seconds" to "run until
stopped" — `cantool.py sniff` (Mac) until Ctrl-C, `can sniff` (ESP32)
until Enter. Each needed a different mechanism:

- **Mac**: plain `KeyboardInterrupt` handling — but `open_bus()` has an
  internal settle delay (slcan's post-open sleep) that sits *outside* a
  try block wrapped only around the receive loop, so a Ctrl-C landing
  during connection setup produced an ugly traceback instead of exiting
  cleanly. Fixed by widening the try to cover `open_bus()` too. Verified
  both cases directly (self-`SIGINT` via `signal.raise_signal` from a
  timer thread, since scripting an actual Ctrl-C isn't straightforward):
  interrupt during connect, and interrupt during the receive loop, both
  now return cleanly.
- **ESP32**: `stdin` is in blocking mode (needed for real-time character
  echo, see the CLI-echo fix earlier this repo's history), so a plain
  `fgetc()` poll inside the sniff loop would just stall waiting for a
  keypress instead of continuing to service `twai_receive()`. Used
  `uart_get_buffered_data_len()`/`uart_read_bytes(..., timeout=0)`
  instead — non-blocking, checked once per loop iteration alongside the
  CAN receive. **Same CRLF-leftover-byte bug as the CLI's
  `run_cli()`/`exit` fix**: the `can sniff` command's own line terminator
  left a stray byte in the UART buffer, which the sniff loop's first
  check picked up as an immediate false "Enter pressed" — sniff stopped
  almost instantly instead of waiting for a real keypress. Fixed with the
  same medicine as before: `uart_flush_input()` right before the polling
  loop starts. Verified: sniff now runs for the intended duration and
  only stops on an explicit Enter sent afterward.
