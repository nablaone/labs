# 2026-08-04

## Fixed the zephyr-canbus Docker image on an x86_64 host

`make` (image build) was failing: `qemu-system-xtensa --version` died with
`Exec format error`. The Dockerfile's QEMU step
(`firmware/zephyr-canbus/Dockerfile`) had the release asset arch hardcoded
to `aarch64-linux-gnu` — a leftover from when that image was last built on
Apple Silicon — but this Linux box is x86_64.

Fixed by picking the asset from Docker's own `TARGETARCH` build arg
(`amd64` → `x86_64-linux-gnu`, `arm64` → `aarch64-linux-gnu`), so the same
Dockerfile now builds correctly on both this box and a Mac. Rebuilt clean;
`qemu-system-xtensa --version` reports `9.2.2` as expected.

Also audited host apt packages while at it: `docker-ce`, `can-utils`, and
`esptool` were already installed here. Added `wireshark` and `picotool`
(the docs call out Wireshark for CAN capture; picotool wasn't installed at
all). Real gap found: this user account wasn't in the `dialout` group, so
`esptool`/serial access to `/dev/ttyACM*`/`/dev/ttyUSB*` would've failed
without `sudo` — fixed with `usermod -aG dialout`.

## SocketCAN setup — found real hardware, and a real udev/systemd gotcha

Asked generically "how to set up SocketCAN" — turned out a CANable2 was
already plugged into this box (`lsusb`: `16d0:117e MCS CANable2`), making
this the de facto CAN-gateway host from
[CLAUDE.md](../CLAUDE.md)'s open questions, at least for now.

**First wrong assumption**: treated it as a candleLight/`gs_usb` adapter
(native CAN netdevice) because that's what CANable2 usually ships as.
`gs_usb.ko` loaded fine but never bound anything. Checked
`/sys/bus/usb/devices/*/idVendor` and found this unit's USB interfaces
bound to `cdc_acm`, not `gs_usb` — it's actually running **slcan/CDC-ACM
firmware** (shows up as `/dev/ttyACM3`, not a `can*` netdevice). Pivoted to
`slcand` to bridge it into SocketCAN instead of reflashing.

**Insight: a udev `RUN+=` key can't reliably spawn a daemon.** Wrote a
udev rule (`ACTION=="add", SUBSYSTEM=="tty", ..., RUN+="slcand ..."`) that
matched correctly under `udevadm test` and worked fine when the exact same
command was typed by hand — but never fired on a real hotplug. Wrote
`scripts/debug-udev-can.sh` (bumps `udevadm` to debug log level, tails
`journalctl -u systemd-udevd` across a live replug) to catch the real
error, since this box has no `adm`/`systemd-journal` group membership so
`journalctl` needed root anyway. The log showed the answer directly:

```
Process '...slcand...' terminated by signal TERM.
Failed to wait for spawned command '...': Input/output error
```

`systemd-udevd` kills a still-running `RUN` command when a *second* uevent
for the same device supersedes the first — this box also runs
ModemManager for its WWAN modem, which briefly touches every new tty
(`ID_MM_CANDIDATE=1` on the CANable2's port too) even after telling it to
ignore this specific device via `ENV{ID_MM_DEVICE_IGNORE}="1"`. `RUN+=` is
only meant for quick synchronous actions; a long-lived daemon has to be
handed off to systemd proper so the udev worker stops tracking it.

**Fix**: a `slcand@.service` systemd template
(`/etc/systemd/system/slcand@.service`), started via
`TAG+="systemd", ENV{SYSTEMD_WANTS}="slcand@%k.service"` in the udev rule
instead of a direct `RUN+=`. Bonus: `BindsTo=dev-%i.device` means the
service stops automatically on unplug too — the old `RUN+=` version had no
way to do that and was leaking one orphaned `slcand` process per replug
(confirmed: found three stray processes bound to the *modem's* other
`ttyACM` ports at one point, from earlier by-hand debugging spilling onto
the wrong device numbers as they kept shifting across replugs).

**Second-order bug caught by the same debug log**: the candleLight/`gs_usb`
rule (`SUBSYSTEM=="net", KERNEL=="can*"`) was *also* matching the
`can*` netdevice that `slcan.ko` creates for the slcand-bridged adapter —
same `KERNEL=="can*"` pattern matches both native and slcan-bridged CAN
interfaces — causing a redundant, failing `ip link set ... up` against an
interface already brought up. Scoped that rule to `DRIVERS=="gs_usb"` so
it only fires for genuine candleLight-firmware adapters.

**Third issue**: even with the systemd unit firing correctly on hotplug,
`can0` first came up registered but `DOWN` (`bitrate 0`) — `slcand -o`'s
own serial "open" handshake apparently lost a race when launched this
close to the port's enumeration (no such issue when a human runs the same
command several seconds later by hand). Added
`ExecStartPost=-/usr/bin/ip link set can0 up type can bitrate 500000` to
the service as an explicit, kernel-level bring-up that doesn't depend on
`slcand`'s own open command succeeding.

End-to-end verified clean (zero manual commands) after all of the above:
unplug → replug → `slcand@ttyACM3.service` auto-starts →
`ExecStartPost` brings `can0` up at 500kbit `ERROR-ACTIVE` → `candump
can0` works → `nmcli device status` shows `can0` correctly `unmanaged`.

Bitrate (500000) is still a placeholder — no firmware speaks CAN yet, so
nothing has forced an actual bus-bitrate decision. It's centralized in one
place (`CAN_BITRATE` in `scripts/setup-socketcan.sh`) for whenever that
gets decided.

Landed as `scripts/setup-socketcan.sh` (idempotent, no `sudo` calls inside
— the `make setup-socketcan` target wraps it) and
`scripts/debug-udev-can.sh` (`make debug-udev-can`), plus a new top-level
`Makefile` for this host-setup tooling, separate from
`firmware/zephyr-canbus/Makefile`'s Docker/Zephyr build targets.
